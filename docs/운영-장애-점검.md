# 서버 장애 점검 가이드 (2026-11-11 농업인의 날 사례)

접속자가 몰린 날 Supabase 가 불안정해졌을 때 **무엇을, 어떤 순서로** 보면 되는지 정리한 문서입니다.
게임은 서버가 안 돼도 오프라인으로 끝까지 플레이되므로, 장애가 나도 서두르지 말고 아래 순서대로 원인을 확인하세요.

> ⚠️ **0단계 — 오늘 안에 로그부터 저장**
> 무료(Free) 플랜은 API·데이터베이스 로그를 **약 1일**만 보관합니다. 다음 날이면 사라지니 오늘 화면을 캡처하거나
> Logs 화면 오른쪽 위 ⬇(다운로드)로 내려받아 두세요.

## 1. 큰 그림: 요청이 지나가는 길

```
태블릿 브라우저
  │  ① OPTIONS (사전 확인: "이 주소로 보내도 되나요?")  ← 브라우저가 자동으로 먼저 보냄
  │  ② POST /rest/v1/rpc/ft_api_xxx
  ▼
API Gateway (Supabase 앞단, Cloudflare)      ← 상태 코드가 여기서 기록됨
  ▼
PostgREST (HTTP → SQL 함수 호출로 바꿔 주는 프로그램, DB 연결 몇 개를 돌려 씀)
  ▼
Postgres (ft_api_* 함수 실행)  ──(학교 검색만)──▶ NEIS 외부 API (최대 3초 대기)
```

같은 무료 서버(작은 가상 머신 1대) 안에 **Postgres, PostgREST, Auth** 등이 함께 돌아갑니다.
그래서 한 프로그램이 CPU·메모리를 다 쓰면, 이 게임이 쓰지도 않는 **Auth 까지 같이 Unhealthy** 가 됩니다.

### 상태 코드 읽는 법

| 코드 | 뜻 | 이 게임에서 |
|---|---|---|
| 200 | 성공 | 우리 함수는 오류도 **200 + JSON**(`{"status":429,…}`)으로 돌려줌 → 200 이라고 다 성공은 아님 |
| 4xx | 요청 쪽 문제 (잘못된 키·권한) | 거의 없어야 정상 |
| 5xx | 서버 쪽 문제 | **장애의 핵심 신호** |
| **520** | 앞단(Cloudflare)이 뒤쪽 서버(PostgREST)에게서 **정상 응답을 못 받음** | 함수가 틀린 게 아니라 **PostgREST 자체가 죽었거나 응답 불능** |
| 504 | 뒤쪽 서버가 너무 오래 걸려 시간 초과 | DB가 느릴 때 |

## 3. 확인 순서 (대시보드)

### ① Logs → 로그 종류별로 메시지 읽기 (가장 중요)
왼쪽 **Log Type** 에서 하나씩만 체크해서 봅니다. 줄을 클릭하면 자세한 내용(metadata)이 펼쳐집니다.

1. **PostgREST** (1.0k건): 아래 같은 문구가 있는지 찾기
   - `connection pool timeout`, `could not connect`, `Database connection lost`, `too many connections`
   → 있으면 **DB 연결이 부족**했던 것 (2번 원인)
2. **Postgres** (오류 116건): **Level = Error** 로 거르고 메시지 확인
   - `remaining connection slots are reserved` / `too many clients` → 연결 수 한계
   - `canceling statement due to statement timeout` → 쿼리가 너무 오래 걸림
   - `out of memory`, `terminating connection` → 메모리 부족
   - `could not serialize` / `deadlock` → 잠금 충돌
3. **API Gateway**: 경로(pathname)별로 520 이 어디에 몰렸는지, 첫 520 이 **몇 시 몇 분**에 시작됐는지 기록

> 줄 하나 읽는 법: `시간 · 상태코드 · 메서드 · 경로 · 이벤트 메시지(주소 | 브라우저 정보)`
> `Mozilla/5.0 (X11; CrOS…)` 는 크롬북, `Linux; Android 10; K` 는 안드로이드 태블릿 → 어떤 기기가 접속했는지도 알 수 있어요.

### ② Reports (보고서) → 서버 자원 그래프
- **Database** 보고서: CPU 사용률, 메모리(RAM), 연결 수(connections) 그래프
  - CPU 가 100% 에 붙어 있음 → 처리 능력 부족
  - 메모리가 꽉 참 + 스왑 증가 → 메모리 부족 (PostgREST·Auth 같이 죽는 대표 원인)
  - 연결 수가 위쪽 한계선에 붙음 → 연결 부족
- **API** 보고서: 시간대별 요청 수와 오류 비율 — 장애 시작 직전 요청이 얼마나 늘었는지

### ③ Advisors → Query Performance
가장 시간을 많이 쓴 쿼리 목록(아래 SQL ⑥과 같은 내용). `ft_api_search_schools`(NEIS 호출)가 평균 시간이 크게 나오면 4번 원인.

### ④ Usage / Billing
무료 한도 초과 경고가 있었는지 (특히 Egress, Logs).

## 4. SQL Editor 에서 직접 확인하기 (복사해서 실행)

SQL Editor 는 읽기만 하는 쿼리라 안전합니다. 서버가 다시 살아난 뒤에 실행하세요.

```sql
-- ① 10분 단위 입장 수 (한국 시간) → 피크 시각
select to_char(date_trunc('hour', started_at at time zone 'Asia/Seoul')
         + floor(extract(minute from started_at at time zone 'Asia/Seoul') / 10) * interval '10 min', 'MM-DD HH24:MI') as 시각,
       count(*) as 입장
from ft_sessions
where started_at > now() - interval '2 days'
group by 1 order by 1;

-- ② 10분 단위 미션 완료 수 (서버에 실제로 기록된 것)
select to_char(date_trunc('hour', completed_at at time zone 'Asia/Seoul')
         + floor(extract(minute from completed_at at time zone 'Asia/Seoul') / 10) * interval '10 min', 'MM-DD HH24:MI') as 시각,
       count(*) as 완료
from ft_session_quests
where completed_at > now() - interval '2 days'
group by 1 order by 1;

-- ③ 오늘 학교별 입장 학생 수 (한 학교 = 공인 IP 하나를 함께 씀)
select school_name, count(*) as 학생수
from ft_sessions
where started_at > now() - interval '1 day'
group by 1 order by 2 desc limit 20;

-- ④ IP 별 최근 1분 호출 수 (분당 1200 제한에 닿은 학교가 있는지)
select key, count, reset_at
from ft_rate_limits
where key like 'rl:ip:%'
order by count desc limit 20;

-- ⑤ 지금 DB 연결 상태 (무엇을 기다리는지)
select count(*) as 연결수, current_setting('max_connections') as 최대 from pg_stat_activity;
select state, wait_event_type, wait_event, count(*)
from pg_stat_activity group by 1, 2, 3 order by 4 desc;

-- ⑥ 가장 시간을 많이 쓴 쿼리 TOP 15 (Advisors → Query Performance 와 같은 내용)
select calls as 호출수,
       round(mean_exec_time::numeric, 1) as 평균ms,
       round(total_exec_time::numeric) as 합계ms,
       left(regexp_replace(query, '\s+', ' ', 'g'), 90) as 쿼리
from pg_stat_statements
order by total_exec_time desc limit 15;

-- ⑦ 쓰기가 많은 표의 정리 상태 (죽은 행이 많으면 느려짐)
select relname, n_live_tup as 살아있는행, n_dead_tup as 죽은행, last_autovacuum
from pg_stat_user_tables where relname like 'ft_%' order by n_dead_tup desc;

-- ⑧ 학교 검색 캐시 (많을수록 NEIS 호출이 줄었다는 뜻)
select count(*) filter (where expires_at > now()) as 유효캐시, count(*) as 전체
from ft_cache where key like 'schoolq:%';
```

## 5. 이 게임의 원인 후보와 판별표

| # | 후보 (코드 위치) | 이렇게 보이면 이것 |
|---|---|---|
| 1 | **실패해도 줄지 않는 요청 (재시도 폭풍)** — 전광판이 10초마다 순위 요청(`client/src/game/Scene.jsx` LeaderboardPoller), 완료 기록은 8초마다 재전송(`store.js` flushPending), 요청마다 OPTIONS 가 한 번 더 | 520 이 나는 동안에도 요청 수 그래프가 줄지 않음, 520 의 대부분이 leaderboard |

| 4 | **학교 검색이 DB 안에서 NEIS 를 최대 3초 기다림** (`ft_api_search_schools` 의 `http_get`) — 수업 시작 때 한꺼번에 검색 | 피크가 입장 직후(①과 그래프 비교), ⑥에서 search_schools 평균 시간이 수백 ms~수 초 |
| 5 | **무료 서버 자원 한계** (작은 CPU·메모리, 다른 프로그램과 공유) | Reports 의 CPU/메모리가 꽉 참, Auth 같은 무관한 서비스까지 Unhealthy ← **이번에 해당** |
| 6 | IP 제한(분당 1200)에 걸린 큰 학교 | ④에서 count 가 1200 근처 — 이 경우는 520 이 아니라 **200 응답 안에 429** 로 나와서 화면에 "오프라인" |

이번 스크린샷만으로는 **5(자원 한계)가 바탕이고 1(재시도 폭풍)이 회복을 막은 것**이 가장 유력합니다.
2·3·4 중 무엇이 방아쇠였는지는 3단계 ①의 PostgREST·Postgres 메시지와 ⑤⑥을 보면 확정할 수 있어요.

## 6. 이번 기회에 배울 수 있는 개념 (추천 순서)

1. **HTTP 상태 코드와 요청 흐름** — 2xx/4xx/5xx, 520·504 의 차이, 브라우저의 CORS 사전 요청(OPTIONS)이 왜 요청 수를 두 배로 만드는지
2. **로그 읽기** — 시간·경로·상태로 거르기, "처음 실패한 시각"을 찾고 그 직전에 무엇이 늘었는지 보기
3. **자원 지표** — CPU·메모리·연결 수 그래프 읽기, 공유 서버에서 한 프로그램이 다른 프로그램을 쓰러뜨리는 현상
4. **커넥션 풀** — DB 연결은 비싸서 몇 개를 돌려 씀 → 느린 요청 하나가 전체를 막는 이유 (DB 안에서 외부 API 를 부르면 안 좋은 까닭)
5. **폴링 vs 푸시** — 10초마다 묻기(폴링)는 사람 수에 비례해 늘어남. 간격 늘리기, 화면을 안 볼 때 멈추기, 결과를 몇 초 캐시하기, 실시간(Realtime) 구독
6. **재시도와 백오프** — 실패하면 점점 더 오래 기다렸다 다시 보내기(지수 백오프) + 무작위 지연(jitter). 다 같이 8초마다 다시 보내면 서버가 회복할 틈이 없음
7. **Rate Limit 과 학교 네트워크(NAT)** — 학교 전체가 공인 IP 하나 → IP 기준 제한은 넉넉하게, 진짜 방어는 세션 기준
8. **우아한 성능 저하** — 서버가 죽어도 게임은 오프라인으로 계속, 완료 기록은 쌓아 뒀다가 나중에 전송. 이번에 실제로 효과를 본 설계

## 7. 다음에 해 볼 개선 (선택 — 아직 적용 안 함)

- 전광판 폴링 간격 30~60초로, 탭이 안 보이거나 오프라인이면 멈춤
- 순위 결과를 DB 에 5~10초 캐시 (수백 명이 같은 결과를 공유)
- 실패 시 재시도 간격을 점점 늘리기 + 무작위 지연
- 순위 조회처럼 읽기만 하는 API 는 Rate Limit 쓰기 생략
- 전국 초등학교 목록을 미리 DB 에 넣어 NEIS 실시간 호출 없애기
- 행사 당일만 컴퓨트를 한 단계 올리기 (Pro 플랜 + Small 이상, 끝나면 내리기)

### 원인 1 (확인됨) — 학교 검색이 학교 전체의 요청을 붙잡고 있었음
1. Supabase 는 브라우저 요청(anon 역할)에 **3초 시간 제한**을 둡니다. 넘으면 강제 취소(57014).
2. 학교 검색 함수(`ft_api_search_schools`)는 ① 먼저 그 학교 IP 의 요청 횟수 행(`ft_rate_limits` 의 `rl:ip:학교IP`)을 고친 뒤 ② **NEIS 응답을 최대 3초 기다립니다.**
   DB 는 고친 행을 함수가 끝날 때까지 잠가 두므로, 그동안 **같은 학교(같은 IP)의 모든 요청**(전광판 순위, 미션 완료, 입장)이 그 행 앞에서 줄을 섭니다.
3. 한 반 30명이 동시에 학교를 검색하면 잠금이 줄줄이 이어져, 뒤에 선 요청은 3초를 넘겨 취소됩니다.
4. 줄 서 있는 요청들은 PostgREST 의 DB 연결을 붙잡고 있어 **연결이 바닥** → 다른 학교 요청까지 막힘 → PostgREST Unhealthy → 전국 520.
5. 게다가 검색 자체도 "NEIS 3초 + 앞뒤 처리"라 3초 제한을 넘기기 쉽고, 시간 초과 취소는 함수 안의 예비 처리(예시 학교 목록)로도 잡히지 않아 **검색이 그냥 실패**합니다.

로컬 DB 에서 재현: 한 요청이 학교 IP 행을 잡은 채 4초 기다리는 동안, 같은 IP 의 순위 조회는 3초 뒤
`canceling statement due to statement timeout … while inserting index tuple … "ft_rate_limits"` 로 취소(로그와 같은 메시지), 다른 IP 는 0.05초에 정상 응답.

### 원인 2 (확인됨) — 실패해도 줄지 않는 요청
전광판 10초 폴링 + 미션 완료 8초 재전송 + 요청마다 OPTIONS. 장애 중 1시간 22,849건 중 POST 대부분이 520 이었는데도 요청 수가 줄지 않았고,
교실에 켜 둔 태블릿이 밤새 계속 요청을 보낸 것으로 보입니다(새벽의 꾸준한 오류).

### 원인 3 (추정) — 무료 서버가 버티지 못하고 Postgres 가 꺼짐
연결이 쌓이고 재시도가 몰리자 작은 무료 서버가 자원을 다 써 Postgres 가 멈춘 것으로 보입니다(Auth 도 같은 서버라 함께 실패).
**정확히 왜 꺼졌는지는 내려받은 오류 로그에 없습니다.** 꺼질 때의 메시지는 오류(Error)가 아닌 일반 로그 단계로 남기 때문입니다.
보관 기간 안이라면 Logs 에서 Postgres 를 11/11 11:00~13:10 으로 좁혀 `terminated by signal`(메모리 부족으로 강제 종료), `out of memory`, `No space left on device`(디스크 가득) 를 검색해 보세요.
Reports → Database 의 메모리·디스크 그래프와 Supabase 가 보낸 메일도 함께 확인하면 좋습니다.

### 증상과 원인 연결
- **학교 검색 안 됨**: 원인 1 (3초 초과로 취소) + Postgres 다운
- **전광판·점수 안 쌓임**: 원인 1 의 잠금 대기 → 520, 이후 Postgres 다운
- **게임은 계속됨**: 오프라인 모드 설계 덕분. 완료 기록은 태블릿에 남아 있다가 서버가 살아난 뒤 다시 접속하면 전송됨

### 고친 내용 (11/12 적용 — Supabase SQL 다시 실행 필요)
- **학교 검색**: 캐시에 있으면 쓰기 없이 응답. 없으면 제한을 '읽기만' 확인하고(잠금 없음) NEIS 를 **1.5초**까지만 기다림. 실패하면 예시 목록을 1분 기억. 호출 기록은 맨 끝에 아주 잠깐만.
- **순위 조회**: 학교 IP 행에 쓰기를 하지 않음. TOP 목록은 5초간 모두가 같은 결과를 함께 씀(내 학교 점수는 항상 최신).
- **태블릿**: 전광판 10초 → **45초**, 화면이 안 보이면 멈춤, 실패하면 간격을 늘림. 미션 완료 재전송은 8초 고정 → **8·16·32초… 최대 5분**(무작위로 흩어서). 학교 검색은 0.4초 쉬었다가.
- **테스트**: `supabase/tests/lock_test.sh` — 같은 학교 요청이 IP 행을 잡고 있어도 순위 조회·학교 검색이 기다리지 않는지 확인(예전 코드는 이 테스트에서 장애와 같은 오류로 실패).
- 값은 `ft_config` 의 `neis_timeout_ms`, `leaderboard_cache_ms` 로 바꿀 수 있어요.
